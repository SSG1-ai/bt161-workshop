Decommission a Legacy Agent

Close out a legacy billing agent: link the ADR and successor, set the lifecycle to End of Life, and reject its verification.

Home Ex 0 Ex 1 Ex 2 Ex 3 Ex 4 Ex 5 Ex 6

Overview

Governance includes formally closing out agents that are no longer needed — not just approving new ones. In this exercise you decommission a legacy billing agent that was replaced by the agent you verified earlier, documenting its lineage and removing its production approval.

Background

The custom Joule Studio agent you governed in Exercises 2–5 was introduced to replace an older agent: the AWS Billing Document Retrieval Agent [PXX], a legacy billing agent built on AWS Bedrock by the Finance Controlling team in 2023 to automate billing document lookups and retrievals for GlobalFlex AG's Quote-to-Cash process (searching for billing documents, checking billing dates, retrieving posting information, and updating billing references via custom REST API endpoints into SAP S/4HANA). It was a valid solution at the time — but it runs on AWS infrastructure outside SAP's security perimeter, and it was built before the Joule Studio runtime policy was established.

The AWS Billing Document Retrieval Agent [PXX] is already in Phase Out lifecycle — but the governance record has not been closed out. Without formal decommissioning, it could still be discovered, reactivated, or mistaken for an active agent.

Your job is to complete the record: link the governing architecture decision, link the successor, update the lifecycle to End of Life, and remove the verification.

1

Find the legacy agent

  1. Click the EA Assistant icon (stars icon) in the header toolbar, next to the Full View switcher.
  2. Use the following prompt:
Prompt to paste (replace [PXX])Find the AWS Billing Document Retrieval Agent [PXX].
  1. Open the fact sheet returned by the assistant.
2

Link the Architecture Decision

The ADR you created in Exercise 1 — "Finance Agents on SAP S/4HANA Must Use Joule Studio Runtime" — is exactly why this agent is being retired. The AWS Billing Document Retrieval Agent [PXX] runs on AWS Bedrock rather than the Joule Studio runtime, so it does not comply with the policy. Linking the ADR here closes the governance loop: the decision that triggered the decommissioning is traceable from the agent's fact sheet.

You can do this in two ways — choose one:

Option A — via EA Assistant (continuing the session from Step 1):

Prompt to paste (replace [PXX])Link my architecture decision [PXX] to the AWS Billing Document Retrieval Agent [PXX].

Option B — from the ADR fact sheet:

  1. Navigate to your ADR ("Finance Agents on SAP S/4HANA Must Use Joule Studio Runtime — [PXX]").
  2. In the Affected Fact Sheets section, add the AWS Billing Document Retrieval Agent [PXX].
3

Set the successor

  1. In the fact sheet Information section, under Relationship Explorer, find the Successors subsection.
  2. Add your verified custom agent as the successor (search by [PXX]).
  3. Set an Active From date matching the Active date you used in Exercise 5.
Note This creates a formal lineage record — the successor's fact sheet will show the legacy agent as its Predecessor.
Why this matters Adding the successor builds a formal lineage record, so future viewers can see exactly what replaced the legacy agent and when. The replacement's fact sheet will then list this legacy agent as its Predecessor.
4

Update the lifecycle to End of Life

  1. Open the Lifecycle field in the fact sheet header.
  2. Set the End of Life phase with today's actual date — this is date-driven, not just a label.
  3. This mirrors how you opened the Active phase in Exercise 5, and drives lifecycle/roadmap reports.
Why set the actual date Because the lifecycle field is date-driven, set the real End of Life date rather than just the phase label. This captures when the agent retired, which feeds the lifecycle/roadmap reports and the Change Log timestamp. It parallels the Active phase you opened in Exercise 5 — you are now closing the lifecycle you began.
5

Reject the verification

An End-of-Life agent should be explicitly rejected — not just unverified — so the record shows a deliberate decision.

  1. Locate the Verification Badge in the fact sheet header.
  2. Click the badge and select Mark as Rejected.
  3. The badge updates to the rejected state.
Reject, don't just unverify An End-of-Life agent shouldn't keep a production-approved badge. Explicitly rejecting — rather than unverifying — records a deliberate governance decision, not just a neutral reset.

Summary

You have completed the full governance lifecycle — from discovering a new agent all the way to formally decommissioning a legacy one. The ADR links the policy decision that drove the retirement; the successor link connects the two agents as a documented lineage; and the decommissioning record is preserved in the Last Updated tab. The legacy agent remains in the inventory as a historical record; it is not deleted. (In a real landscape you would typically archive the fact sheet after a retention period, which removes it from active views while keeping its history.)

From discovery to decommissioning This is what the session title means by "from discovery to decommissioning" — governance is a continuous cycle, not a one-time event.
